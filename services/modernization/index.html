The idea behind this service

The strangler fig

Move capability gradually; retire the old path only after its replacement has been checked.

The strangler fig approach grows replacement capabilities around an existing system. A routing layer directs selected work to the new path while other work stays on the old one, allowing owners to validate each transition before retiring what is no longer needed.

What it is

Modernization changes an existing system or process while accounting for the work that depends on it. The starting point is a map of current responsibilities, data and connections, not an assumption that everything should be replaced.

For a suitable system, the strangler fig approach moves selected work through new capabilities in stages. This service may also involve an upgrade or process redesign; the agreed slice does not promise to remove every legacy dependency or organizational bottleneck.

What winning looks like

Dependencies made visible

Do affected owners understand which workflows, data consumers and connections could be disturbed by the selected change?

You would see: Inspect a current-state map with system owners and downstream dependencies.

A bounded transition

Can the team explain which capability moves first, what remains in place and how it will judge whether the new path is acceptable?

You would see: Review a migration plan with a selected slice and transition checks.

Data and continuity checks

Have owners agreed how to check data consistency and ongoing work while old and new capabilities coexist during the transition?

You would see: Ask for reconciliation results and workflow checks for both paths.

Retirement with conditions

Are rollback responsibilities and the conditions for retiring an old capability explicit, including dependencies that prevent removal?

You would see: Read the rollback plan and retirement checklist signed off by affected owners.

How we'll achieve it

  1. Map

    Understand the current landscape

    Walk through the existing systems and processes with their owners. Identify what each supports and where the limitations affect business work.

    Output: Current-state system and process map with known limitations.

  2. Assess

    Trace transition risks

    Identify data dependencies, connected systems and acceptable transition windows. Discuss migration and rollback responsibilities before choosing the change.

    Output: Dependency register and transition risk assessment with accountable owners.

  3. Prioritize

    Choose a manageable replacement

    Rank candidate changes and select a bounded capability or process improvement. Define what stays in place and how the transition will be checked.

    Output: Modernization roadmap with the first slice, milestones and validation criteria.

  4. Implement

    Introduce the agreed slice

    Build the scoped upgrade or replacement and route selected work to it where appropriate. Preserve a defined fallback while validating the transition.

    Output: Implemented slice with migration instructions and a documented fallback procedure.

  5. Validate

    Review the transition before retirement

    Check workflow behaviour and data with the affected owners. Record remaining dependencies and agree whether the old capability can be retired.

    Output: Transition review with data checks, handover notes and a retirement decision.

Practice we build on

Replace capability incrementally — Strangler Fig Application

Fowler’s strangler fig approach replaces an existing system gradually by introducing new functionality around it. The old system can shrink as replacement capabilities take over its responsibilities.

Choose the migration treatment — AWS migration strategies

AWS describes retire, retain, rehost, relocate, repurchase, replatform and refactor as migration strategies. Distinguishing them helps owners choose a treatment for each application rather than apply one move everywhere.

Keep each transition small — DORA’s software delivery metrics

DORA recommends reducing the batch size of changes to make them easier to understand, move through delivery and recover from if they fail. This informs the size of a migration increment.

In scope for this service

Who this fits

Teams responsible for existing systems or processes whose limitations make change difficult.

What the work can cover

Review the current system/process landscape and agree a staged change: a system upgrade, migration, process redesign or combination. Use AI only where its value can be assessed.

Typical deliverables

A menu to agree in scope, rather than a fixed package.

  • A review of the current systems, processes, and dependencies
  • A prioritized modernization roadmap with migration risks and milestones
  • A scoped system upgrade, process redesign, or migration
  • Validation and handover plans for the systems and teams affected

How an engagement can work

  1. Map the current state
  2. identify dependencies and transition risks
  3. prioritize changes
  4. implement the agreed slice
  5. validate the transition with affected owners

What we need to understand

  • Current system documentation and a walkthrough of the work
  • Known bottlenecks, technical constraints, and business priorities
  • Data migration needs, system owners, and acceptable transition windows

Start with a description. Agree data handling and access before sharing confidential materials.

Expected outcome and boundaries

A defined improvement with an understood transition. Evaluate agreed workflow checks, data validation and continuity requirements; keep remaining limitations visible.

Choose measures and acceptance criteria together before building. These are aims and evaluation questions, not guaranteed results.

Scope and constraints

A scoped modernization project does not promise to replace every legacy system or remove all organizational bottlenecks. Migration, rollback and transition responsibilities require agreement.

Deliverables, access, responsibilities, schedule, pricing, IP terms, and any further support belong in the agreed scope.

Questions

Must we replace the whole system?

Review may support an incremental upgrade instead.

Where do integrations fit?

A single handoff may fit automation; modernization addresses the broader system/process change and its transition.

Do we need to replace the entire system?

An incremental upgrade, migration or process redesign may address the agreed limitation. Mapping the current landscape helps identify what should remain and what needs to change.

Can the old and new systems run together?

Coexistence can support a staged transition when the architecture and data allow it. Routing, data consistency, fallback and the duration of overlap need explicit design and ownership.

When can an old capability be retired?

Retirement follows agreed workflow and data checks, a review of remaining dependencies and an owner’s decision. Completing a new component alone is not enough evidence to remove the old path.
