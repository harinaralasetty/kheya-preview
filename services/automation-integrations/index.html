The idea behind this service

The handoff map

Name the trigger, the receiving system, the human decision and the route for failure.

A handoff map follows work as it moves between people and tools. It identifies what a machine may do, where a person must approve and where an exception goes, so connecting systems does not obscure responsibility for the task.

What it is

Automation connects repeatable steps that currently depend on people moving information between tools. A useful starting point is one workflow with a clear trigger, a known destination and examples of what happens when the handoff fails.

The handoff map includes people as part of the system, with explicit approvals and manual exception paths. Usable interfaces and approved access are prerequisites; AI is optional, and delivering an automation does not establish indefinite operation of it.

What winning looks like

A traceable handoff

Can an owner follow a task from its trigger to the receiving tool and see which step accepted, rejected or delayed the work?

You would see: Trace a sample run through its action log and matching destination record.

An explicit approval point

Is it clear which actions can run automatically and which need a person’s decision before the connected system may proceed?

You would see: Inspect the permission rules and a test run that pauses for approval.

Failures with somewhere to go

What happens when a tool is unavailable, a request repeats or the input cannot be processed, and who is responsible for resolving it?

You would see: Review failed-run examples, retry limits and the manual exception queue.

Measures tied to the workflow

Have owners chosen how to count completed handoffs, manual interventions and surfaced failures before interpreting the automation’s behaviour?

You would see: Ask for agreed measure definitions and a review of recorded workflow runs.

How we'll achieve it

  1. Observe

    Follow the repeated task

    Walk through the trigger, tools and receiving steps with the people doing the work. Include examples of exceptions and unsuccessful handoffs.

    Output: Workflow map with triggers, system interfaces and observed exceptions.

  2. Bound

    Set action and exception rules

    Agree approved access, allowed actions and decisions that stay with people. Define retry limits, escalation and what must remain manual.

    Output: Action and approval matrix with exception rules and named owners.

  3. Connect

    Implement the approved handoffs

    Connect the agreed systems and preserve the information needed to trace each run. Make approval points and failure routes part of the implementation.

    Output: Scoped integration with action logs and configured approval steps.

  4. Exercise

    Test ordinary and failed runs

    Run normal cases alongside repeated inputs, unavailable tools and rejected approvals. Check that failures are visible and actions stay within scope.

    Output: Normal and failure-case test results with recorded follow-up issues.

  5. Transfer

    Review results with workflow owners

    Review the selected measures and unresolved exceptions. Document how the receiving team handles failures and who operates the workflow after handover.

    Output: Workflow review, operating instructions and exception-handling handover notes.

Practice we build on

Describe the process consistently — Business Process Model and Notation

Business Process Model and Notation is a standard notation for describing processes. Its events, activities and decision points give participants a shared way to discuss how work moves.

Design for repeated and failed messages — Enterprise Integration Patterns

Enterprise Integration Patterns describes an Idempotent Receiver, which handles repeated messages without repeated effects, and a Dead Letter Channel for messages that cannot be delivered. These patterns make failure handling part of integration design.

Measure the outcome of a handoff — Google SRE Workbook: Implementing SLOs

A service level objective is a reliability target tied to what users need. The SRE Workbook describes choosing indicators and reviewing targets, helping owners judge whether a workflow is delivering its intended service.

Expected outcome and boundaries

A controlled, testable workflow. Candidate measures include manual interventions, successful handoffs and how clearly failures are surfaced; choose measures before building.

Choose measures and acceptance criteria together before building. These are aims and evaluation questions, not guaranteed results.

Scope and constraints

Automation needs usable interfaces and approved access. Exceptions may remain manual. Implementation does not establish permission for unrestricted actions or operation of the workflow indefinitely.

Deliverables, access, responsibilities, schedule, pricing, IP terms, and any further support belong in the agreed scope.

Questions

Does every step need automation?

Keep human decisions where they matter.

How does this differ from FDE?

Automation names the solution type; FDE names an alongside-the-team delivery approach and can include automation when the workflow requires it.

Does the workflow need AI?

Predictable rules and existing tool interfaces may be sufficient. Consider AI only if the task calls for it and its behaviour can be evaluated within the agreed action limits.

What happens when a connected tool fails?

Define how a run is recorded, whether it may retry and who receives the exception. Some cases should stop for a person instead of continuing with incomplete information.

Can the automation take any action our tools allow?

Permission is limited to the approved workflow and its agreed actions. A technical connection does not authorize broader access, and human approvals remain where the owners require them.
