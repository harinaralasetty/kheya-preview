The idea behind this service

The thin slice

Make one narrow journey work from interface to data before widening the application.

A thin slice is a small but complete user journey through the interface, business rules and stored data, prepared for deployment. It gives people something concrete to review before more features are added, while keeping unfinished scope explicit.

What it is

Custom software creates an application around a user task that existing tools do not adequately support. The first scope can be narrow while still connecting the screen, the business rules and the data needed to finish that task.

A thin slice is not a collection of disconnected screens or a promise to deliver every future feature. Features, integrations, deployment responsibility and operating ownership are agreed explicitly; handover does not establish an ongoing maintenance commitment.

What winning looks like

A complete user task

Can a representative user finish the selected journey, including its important error cases, without relying on an unfinished part of the application?

You would see: Watch a task walkthrough against the agreed acceptance examples.

A scope people can inspect

Are the first release and the deferred features clearly separated so reviewers know which behaviour is included in their decision?

You would see: Compare the scoped journey map with the backlog of deferred work.

Connected and tested layers

Do checks cover the business rules, connections and user journey in a way that makes a failing requirement possible to locate?

You would see: Ask for test results linked to requirements and examples of integration failures.

A usable handover

Can the receiving team identify how the application is deployed, who operates it and which limitations still need a decision?

You would see: Review deployment instructions, ownership notes and the list of known limitations.

How we'll achieve it

  1. Define

    Choose the user journey

    Understand who uses the software and what they need to finish. Agree a manageable first scope and examples that describe acceptable behaviour.

    Output: User journey map with first-release scope and acceptance examples.

  2. Design

    Connect interface, rules and data

    Design the screens, application structure and required connections for that journey. Check data access and operating constraints before building.

    Output: Interface designs and an application design showing the required integrations.

  3. Build

    Review a working slice

    Build the selected journey across its layers and review it with the decision owners. Keep discoveries and requested additions visible in the scope.

    Output: Working application slice and a review log of decisions and deferred requests.

  4. Test

    Check the agreed behaviour

    Test representative tasks, errors and relevant quality requirements against acceptance criteria. Record failures for resolution or explicit review.

    Output: Acceptance results with reproducible failures and unresolved issues.

  5. Handover

    Prepare the release and receiving team

    Prepare deployment for the agreed environment and document the delivered application. Confirm operational ownership and any separately agreed support.

    Output: Deployment instructions, technical documentation and handover checklist.

Practice we build on

Read delivery through four measures — DORA’s software delivery metrics

DORA’s original four keys track deployment frequency, lead time for changes, change failure rate and time to restore service: how often releases happen, commit-to-production time, the share causing failures and recovery duration.

Keep the slice ready to deploy — Continuous Delivery

Continuous delivery brings build, test and deployment work into everyday development. Keeping changes deployable lets a team seek feedback on working software throughout delivery.

Check each layer deliberately — The Practical Test Pyramid

The test pyramid combines many small, focused checks with fewer broad checks of connected behaviour. It helps a team find failures without depending entirely on slow tests through the interface.

Questions

Can the first version be small?

A defined feature or user journey can form the scope.

How does this differ from FDE?

Development describes the software being built; FDE emphasizes working alongside the client's team to integrate and test solutions in its actual workflow.

What belongs in the first release?

Choose a task that matters to users and can be completed within an agreed scope. Include the connections and error handling it needs, while keeping later features on a separate list.

Does a thin slice skip design or testing?

The slice still needs an interface, application design and checks across its layers. Narrowing the journey changes the amount of behaviour being built, not the need to examine it.

Who maintains the application after handover?

Operating responsibility and maintenance need explicit agreement. The delivery scope should name the receiving owner and describe any support that has been agreed separately.
