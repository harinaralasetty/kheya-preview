The idea behind this service

Earned autonomy

Allow more freedom only when task evidence supports it, with a route back to human control.

Earned autonomy treats a system’s freedom as a permission to justify, not a default setting. Begin with a bounded task and human review, examine failures as well as useful outputs, and expand or reduce allowed actions only through an explicit owner decision.

What it is

An AI system may help with language, search, documents or decision support when its usefulness can be examined for a specific task. First define the input, the desired output and a simpler baseline against which to compare it.

The engagement produces a scoped prototype and evidence about its limits, including unsupported or unsuccessful results. A prototype is not ready for release merely because it works on selected examples; no model, accuracy rate or autonomous decision authority is promised.

What winning looks like

A reason to use AI

Does the task assessment explain why an AI approach is worth testing against a simpler method, with a clear definition of a useful result?

You would see: Read the task definition, baseline examples and comparison criteria.

Approved and suitable inputs

Are data access, document suitability and update handling clear enough to test the proposed system without assuming permissions it does not have?

You would see: Inspect the approved data inventory, access rules and update-handling design.

Failures kept in the evidence

Do the evaluation examples include difficult inputs, unsupported claims and reviewer effort as well as outputs that appear useful?

You would see: Review the evaluation set, output assessments and a log of unsuccessful cases.

Authority tied to a decision

Can an owner explain the current action limits, what evidence would justify changing them and how human review would be restored?

You would see: Ask for the permission record, review requirements and conditions for stepping back.

How we'll achieve it

  1. Define

    Specify the task and comparison

    Describe useful outputs and the decisions they might inform. Establish a non-AI baseline and agree the quality questions the prototype must answer.

    Output: Task brief with baseline examples and evaluation criteria.

  2. Inspect

    Review the approved data

    Examine representative inputs, their suitability and access constraints. Decide whether source references are needed and how updates would be handled.

    Output: Data suitability review with access rules and reference requirements.

  3. Prototype

    Build within the agreed limits

    Prototype the selected task using approved data and explicit review steps. Keep model choices and available actions within the scoped experiment.

    Output: Scoped prototype with documented data handling and human review controls.

  4. Evaluate

    Examine useful and difficult cases

    Assess representative tasks and challenging inputs against the baseline. Record unsupported answers, failure handling and the work required from reviewers.

    Output: Evaluation report with assessed outputs, failure cases and reviewer observations.

  5. Decide

    Document limits and the next step

    Review what the evidence supports and where it is insufficient. Decide whether to stop, revise or scope further work, keeping any authority change explicit.

    Output: Limitations register and owner-reviewed decision on further development.

Practice we build on

Organize risk work around the task — NIST AI Risk Management Framework

The NIST AI Risk Management Framework organizes risk work through Govern, Map, Measure and Manage. These functions help teams establish responsibilities, understand context, assess risks and decide how to address them.

Design against model application risks — OWASP Top 10 for LLM Applications

OWASP’s Top 10 for large language model applications describes risks such as prompt injection and sensitive information disclosure. These are design and evaluation concerns when an application accepts content or exposes information through a model.

Keep service expectations measurable — Google SRE Workbook: Implementing SLOs

The SRE Workbook links reliability objectives to user needs and an ongoing review process. Applied to an AI service, this informs operational measures; it does not replace evaluation of the content a model produces.

In scope for this service

Who this fits

Teams evaluating language, search, document-processing, assistant or decision-support tasks.

What the work can cover

Assess the use case and approved data; design and prototype a scoped system; define evaluation, access, update handling and human review. Source references apply where the use case requires them.

Typical deliverables

A menu to agree in scope, rather than a fixed package.

  • A use-case assessment, data review, and design for the agreed AI system
  • A scoped AI prototype, with source references where the use case requires them
  • Data access controls, update handling, and human review steps
  • An evaluation set for output quality, failure cases, and unsupported claims

How an engagement can work

  1. Define the task and baseline
  2. inspect data suitability
  3. prototype
  4. evaluate representative and difficult cases
  5. document limits and decide the next step

What we need to understand

  • Representative data or documents approved for the project
  • Examples of the task and what a useful result looks like
  • Data owners, access rules, and review requirements

Start with a description. Agree data handling and access before sharing confidential materials.

Expected outcome and boundaries

Evidence of whether AI helps this task. Evaluate relevant accuracy, source support, failure handling and reviewer effort; retain unsupported or unsuccessful results in the assessment.

Choose measures and acceptance criteria together before building. These are aims and evaluation questions, not guaranteed results.

Scope and constraints

A prototype is not a release-ready system. AI outputs can be wrong; review requirements depend on intended use. No model, accuracy rate or autonomous decision authority is promised here.

Deliverables, access, responsibilities, schedule, pricing, IP terms, and any further support belong in the agreed scope.

Questions

Do we need AI?

A simpler method may fit better.

Can it answer from our documents?

Assess approved sources, access rules, retrieval quality and reference requirements before choosing a design.

What if a simpler method is sufficient?

Use the baseline comparison to make that visible. The assessment can conclude that rules, search or a process change fits the task without further AI development.

Can the prototype answer using our documents?

Assess approved documents, retrieval quality, access restrictions and reference requirements first. A source reference can help a reviewer inspect an answer, but the answer still needs evaluation.

Does successful evaluation permit autonomous action?

Evaluation informs a separate permission decision by the responsible owners. Allowed actions, human review and the conditions for withdrawing permission must be defined for the intended use.
